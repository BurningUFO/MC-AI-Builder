# Builder 的高层决策

原先的聊天通常只生成一次意图，后台规划只在小屋屋檐之间选择。现在真实模型读取任务状态，选择技能，再根据 Forge 返回的结果作下一步决定。运行时最多发起五次模型决策，每次规划租约接受一次改变执行的策略。

## 模型可以决定的事

- 通过「查询任务」读取建筑、进度、NPC 活动、失败证据、库存和下一目标附近的实际方块。模型用这些信息回复玩家，也可以在已有图像共享授权时请求一次配对的 NPC 画面。
- Forge 从已批准队列中按楼层和局部坐标划分待施工组。模型可以把一组尚未开工、已有下方支撑的放置动作提到前面。
- 施工长期无进展或有限重试耗尽时，Forge 暂停在检查点并给出失败证据。模型可换施工组、优先尝试高处站位、优先搭脚手架，或请求临时移开由 Builder 安装且可安全恢复的覆盖块。同一进度点的自动恢复最多接受三种不同策略。
- 缺料时，模型可以安排到授权仓库取成品，调用现有配方制作下一步所需物品，或者向玩家说明实际缺口。新建、复现和改图沿用现有审阅流程。

## 执行与恢复

后台模型请求和游戏施工并行运行。Forge 应用策略前核对玩家、任务、版本、租约及现场条件，并保留已完成与正在执行的队列前缀。寻路、射线、保护区、工具、库存、配方、施工检查点和最终逐格校验由现有执行器负责。涉及权限或玩家主动暂停的情况继续走现有控制入口。

SQLite 保留对应任务的批准目标、最近决策、失败结果和少量观察事实。Forge 检查点保存实际队列、进度和已用恢复策略。重启后，已应用的顺序可以读回，施工按原有检查点流程恢复。真实提供方默认启用后台决策，可用 `--no-planning` 关闭后台调用。`fixture` 仍用于离线演示。

## 验证

离线模拟覆盖 507／1478 进度问答、技能失败后换策略、修改施工队列、取料与制作选择、并行施工、过期结果拒绝和重启读回。现有 Python 测试及 Forge 离线构建共同检查原功能。
