# M7-P 真实施工和并行规划验收

## 对照条件

三组从同一份正常保存的 BMC4 合成地形副本开始，使用同一份 7×9 住宅状态表、同一块批准区域及同一份供料箱库存。测试脚本在计时前清理住宅占地内的草和少量游荡的原版动物。依照玩家许可，测试客户端通过真实玩家身份提交施工区、仓库和建筑审阅。施工通过 Fake Player 原生放置与箱子交互完成。

A 用 M7-A 执行顺序。B 用相邻放置调度、局部行序和分批供料。C 在 B 的基础上允许真实 Codex 调整一个尚未开始的屋顶工作组。A、B 的设计由确定性测试夹具生成。C1 的住宅设计来自真实视觉勘察。后续 C 组复测在新副本中复用 C1 产生的同一设计，并由测试玩家重新审批。所有候选先通过同一份 183 方块 ID、局部坐标和状态表校验。

## 首次真实规划

C1 的模型根据第 6 块时配对的 NPC 第一人称画面请求再观察。第二帧配对时已经完成 41 块。模型指出后侧有一级高差，且画面不足以判断入口通行及后侧作业空间，因此保留原顺序。两次回合之间 NPC 持续施工，完整策略窗口内放置 57 块，最终 183 块全部核验通过，施工耗时 102.96 秒。

复测前将相机取样原点与住宅局部坐标系对齐，并补充 Forge 核对的工作组周边可站格统计。C2 暴露了 Python 读取配对字段位置的错误，安全回退后仍按确定性顺序完成 183 块，耗时 102.93 秒。该次复测没有发送图片或发起模型回合。字段解析按真实 Forge 记录修复，进入工作组时仍由原生施工层逐块检查路径、支撑、碰撞、交互距离和库存。

## 策略落到原生施工

C3 在实际施工到 6 块时配对取得 NPC 路线视角。图像与 Forge 现场样本取自同一游戏 Tick。模型选了 `roof_rear`，协调器重新检查版本、站位、仓库和待施工方块后提交顺序调整。B 组的第一块屋顶位于局部坐标 `[-3, 3, -4]`，C3 的原生第 121 个放置动作移到 `[-3, 3, 0]`。模型思考窗口经过 12.02 秒，Minecraft 在此期间记录了 40 次成功的真实放置，首末两次放置相隔 10.75 秒。模型的理由明确使用了坐标换算，将画面中的石砖定位在前侧，并引用后侧的 49 个已核对站位。最后的逐块回读验证了完整的 183 方块住宅。

## 故障和回归

- C3 的真实 Bridge 拒绝了未知工作组及已提交策略的重复结果，分别返回 `invalid_planning_group` 和 `stale_planning`。同一 Runtime 记录 Bridge 断开并重新连上正常重开的 BMC4。183 块终态、NPC、背包、仓库、施工日志和已采用策略逐项核对一致。主世界施工区因测试玩家离开维度而卸载时，施工日志没有新增动作。返回后恢复原库存和全部核对结果。
- C2 实景测试覆盖了相机配对与坐标注册失败后的回退。离线测试覆盖模型超时、无效决策、预算耗尽和过期策略。
- 最小 Forge 的 M1、M3 和 M4 游戏回归通过，覆盖 30 块窗墙的真实物品交互、不可达、取消、权限、审批、改版、冲突、箱内物品变化、缺料补给、工具耗尽、运输中断及拆换间重启。
- 61 项 Python 离线测试与 Forge 离线构建通过。使用 `tests.m7_p_bench` 跑原顺序和确定性优化，用 `tests.m7_p_live` 跑有单独额度约束的实景策略和重开核对。

## 当前支持范围

并行规划可在获准的 BMC4 副本内为经批准的单层住宅调整一组屋顶靠边方块的先后顺序。每个建筑版本有一份限时策略。玩家意见、进度、材料和可选的 NPC 第一人称帧为决策提供上下文。默认执行已有施工队列。模型请求使用独立线程及现有额度账本。相机只能观察 NPC 当前施工路线，并受共享选项限制。新增、替换、拆除及供料授权继续走已有审阅流程。

隔离副本的源场地已核验相同。另对本机配置中的四份正式存档及源模组目录做逐文件哈希校验，前后结果一致。
