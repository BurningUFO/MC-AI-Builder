# M2 动态修改与施工协调

M2 从 M1 的放置和验收结果继续。施工仍由游戏内 NPC 完成，服务端通过实际物品交互和受约束的拆除交互执行。

## 1. 固定模型版本和施工记录

- 使用 `building_id`、`building_version` 和模型内容哈希标识不可变版本。保存原点、朝向、批准范围和最后成功验收的版本。
- 按 `job_id` 持久记录目标坐标、交互前后的实际状态、NPC 和材料消耗。重启后先核对世界和最后一条记录，再决定恢复点。
- 建立与版本绑定的暂停和取消状态。服务端在每次动作前核对活动版本，切换版本时先停止导航并封存旧队列。

## 2. 生成可审阅的变更计划

- 对比已批准的旧目标、候选新目标及当前世界，按坐标列出保留、补建、拆除、替换和冲突。
- 对每个受影响块保存预期旧状态。提交候选计划后由玩家批准具体的受影响范围和版本；实际状态与预期不一致时将该位置标为冲突。
- 使用基础、支撑物、依附物之间的关系排序。拆除时从依附物开始，放置时从支撑物开始。对联动方块定义一次交互的允许变化范围。

## 3. 实际执行和恢复

- 为 NPC 增加沿用现有导航、攻击距离、工具栏和 Forge 破坏事件的拆除动作。核对工具耐久与掉落。替换由拆除和放置两个有状态步骤组成。
- 动作执行前复查边界、所有权、状态和玩家冲突。记录完成的拆除、已消耗物品和剩余任务，提供有上限的重试。
- 增加对失败后的可读报告及恢复流程。中断后出现玩家编辑时暂停受影响步骤，交回给玩家确认。

## M2 验收用例

从独立世界的 M1 窗墙开始。暂停施工，将窗户改成另一种原版方块，审阅差异后批准。NPC 用真实交互拆换目标，原有墙体和批准区域外的方块完成回读。再覆盖旧指令重放、玩家占用目标、拆除后重启及替换失败四个用例。
