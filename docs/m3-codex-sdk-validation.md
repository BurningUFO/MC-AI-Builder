# M3 Codex SDK 接入验证

项目虚拟环境安装并验证了官方 `openai-codex 0.171.0` 与配套 `openai-codex-cli-bin 0.171.0`。SDK 识别已有 ChatGPT 登录，账号计划标识为 `prolite`。两轮调用前都检查了 ChatGPT 认证类型、官方端点和隔离设置。SDK 进程的 API Key 环境变量为空。 [官方 SDK](https://github.com/openai/codex/tree/main/sdk/python) · [安装包](https://pypi.org/project/openai-codex/0.171.0/)

| 测试 | 回合耗时 | 输入 token | 输出 token | 结果 |
| --- | ---: | ---: | ---: | --- |
| A 独立 `Codex().thread_start()` 和 `thread.run()` | 5.23 秒 | 10,355 | 29 | 返回宽 8 格、使用云杉木板的窗墙参数。 |
| B `CodexProvider` 到候选模型 | 6.67 秒 | 11,333 | 127 | 识别 V1 的局部修改意图，生成 30 块的候选，只把 4 个窗格改成蓝色染色玻璃。 |

共发起 2 个模型回合。B 含 SDK 启动、配置检查和本地候选生成的耗时为 10.16 秒。该轮发送的建筑上下文为 528 字节。SDK 在调用前后均将主 7 天窗口报告为已用 13%。token 来自 SDK 的回合明细，额度百分比来自账号窗口。

两次使用 `Sandbox.read_only`、`ApprovalMode.deny_all` 和临时会话。生效配置检查确认 shell、继承的 MCP、搜索和通知命令处于关闭状态。B 的返回项只有应用传入的上下文和模型消息，候选由本机 `Wall` 校验器和 `Building` 生成器构建。两轮只用合成建筑文本，记录保存在忽略目录 `.cache/m3-codex-sdk`。

复用时发现 0.171.0 的计划工具开关需要 `.enabled` 字段，并且 MCP 空表会保留继承条目。现有集成按实际接口设置开关，逐项关闭继承服务，再检查生效配置。后续提案仍走 Forge 人工审批与 M2 版本核验。

上述两轮是独立 SDK 接入测试，用量单独记录。

## 真实游戏调用

SDK 模型列表确认 `gpt-6.2-sol` 可用并支持 `medium`。每轮在发送游戏需求前检查原生 `thread/start` 回报，确认模型和思考深度生效、沙箱只读且审批为 `never`。原生回合再次传入同一个模型与深度，监听路由事件。所有实测回合都使用 ChatGPT 登录，模型工具关闭，API Key 环境变量为空。输入是有限的合成建筑需求和过滤后的游戏上下文。
